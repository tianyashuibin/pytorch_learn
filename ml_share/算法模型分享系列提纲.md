# 算法模型分享系列提纲

整理日期：2026-10-13

## 系列目标与主线

本系列拆分为三场，串联机器学习基础、模型训练、GPU 执行和大模型推理服务。

核心主线：**一个模型如何从数据中学到参数，又如何把一次预测变成 GPU 上的计算，最终支撑多个用户的推理请求？**

建议听众：具备基本 Python 编程经验，希望理解模型训练、推理与 GPU 执行的工程师。每场建议 60～90 分钟，具体深度可根据听众基础调整。

三场安排：

| 场次 | 主题 | 核心问题 |
| --- | --- | --- |
| 第一场 | 模型如何学习：机器学习、训练流程、Embedding 与 MLP | 模型是什么，参数如何学出来？ |
| 第二场 | 模型如何执行：PyTorch、GPU、算子与性能优化 | forward 如何变成 GPU 计算，如何找到性能瓶颈？ |
| 第三场 | 大模型如何生成和服务：Transformer、KV Cache、推理优化与 vLLM | 一个 token 如何生成，多个请求如何高效执行？ |

贯穿案例：使用一个小型推荐模型，从特征、张量 shape、PyTorch 代码、训练迭代，一直追踪到 GPU kernel 和性能分析。第三场再用 Transformer 扩展到生成模型。

## 第一场：模型如何学习

### 分享目标

理解机器学习的基本流程，能读懂 Embedding + MLP 推荐模型，并解释一次训练迭代如何更新参数。

### 1. 机器学习解决什么问题

- 学习方式：监督学习、无监督学习、强化学习。
- 任务类型：分类、回归、排序、生成。
- 区分学习方式和任务类型：分类、回归不是机器学习的全部分类。
- 完整流程：数据 → 特征 → 模型 → 损失函数 → 训练 → 评估 → 推理。
- 数据、模型结构和训练策略如何共同影响效果。
- 训练集、验证集、测试集的用途。
- 过拟合、泛化，以及数据泄漏的基本概念。

### 2. 模型训练的基本概念

- 参数：权重、偏置，以及 Embedding 表中的向量。
- 模型结构：层数、隐藏维度、激活函数。
- 损失函数：衡量预测与目标的差异，例如二分类交叉熵、均方误差。
- 梯度：损失对参数的变化率。
- 反向传播：利用链式法则计算梯度。
- 优化器：SGD、Adam，以及根据梯度更新参数的方式。
- 超参数：学习率（lr）、batch size、训练轮数、正则化等。

### 3. 一次训练迭代

基本过程：

**读取一个 batch → 清理梯度 → forward → loss → backward → optimizer.step → 更新权重。**

- forward：根据输入和当前参数计算预测。
- loss：比较预测结果与标签。
- backward：计算参数梯度。
- optimizer.step：使用梯度更新参数。
- 梯度默认会累积，常规训练需要在适当位置清理梯度。
- 学习率如何影响训练稳定性与收敛速度。
- 训练和推理的区别：梯度计算、参数更新、Dropout、BatchNorm 等。
- `model.eval()` 设置评估行为；`no_grad()` / `inference_mode()` 控制梯度相关开销，两者用途不同。

### 4. 推荐系统中的 Embedding + MLP

示例结构：

**用户/物品特征 → Embedding → 特征拼接或交互 → MLP → 预测分数。**

- 推荐系统的常见阶段：召回、排序；本案例聚焦排序中的点击率预测。
- Embedding：把离散 ID 映射为可学习的向量。
- MLP：矩阵乘法、加偏置、激活函数和多层变换。
- 输入、Embedding 输出、拼接结果和预测输出的 shape。
- 输出分数与业务目标的关系，例如点击概率。
- Embedding 查表与稠密矩阵计算的差异，为第二场的性能分析做铺垫。

### 演示建议

1. 实现一个简短的 PyTorch Embedding + MLP 模型。
2. 打印各阶段张量 shape。
3. 展示一次 forward、loss、backward 和参数更新。
4. 比较更新前后的参数与损失。
5. 用训练集与验证集损失曲线解释过拟合。

### 建议时间分配（约 75 分钟）

| 内容 | 时间 |
| --- | --- |
| 机器学习任务与流程 | 15 分钟 |
| 参数、梯度、优化器和超参数 | 20 分钟 |
| 推荐模型结构 | 15 分钟 |
| 训练演示 | 15 分钟 |
| 讨论与问答 | 10 分钟 |

## 第二场：模型如何执行

### 分享目标

理解 PyTorch 如何把模型计算交给 GPU，认识 GPU 的执行结构，能用性能分析工具定位主要瓶颈。

### 1. 从模型调用到 forward

- `nn.Module`、Tensor、设备（CPU / CUDA）和 dtype。
- 调用 `model(x)` 如何进入 `forward()`，以及模块调用对 hooks 等机制的支持。
- forward 定义模型计算逻辑；完整推理还包含预处理、设备与精度设置、执行和后处理。
- 继续使用第一场的推荐模型，逐个识别张量操作。

### 2. PyTorch 的执行路径

- eager 模式：逐个执行张量算子。
- dispatch：根据设备、数据类型及其他 dispatch key 选择相应实现。
- 算子如何进入底层库或 GPU kernel，例如矩阵乘法调用相关计算库。
- GPU 工作通常异步提交；同步发生在需要等待结果等位置。
- `torch.compile`：计算图捕获、编译和优化的基本过程。
- 图编译的收益：减少 Python 开销、融合算子、减少中间数据等。
- 图中断、动态 shape 和编译开销可能影响实际收益。

### 3. GPU 的基本结构

- SM：执行线程块的计算单元。
- thread、warp、block、grid 的关系。
- 寄存器、共享内存、缓存和显存的用途。
- Tensor Core 与矩阵计算。
- GPU 适合大量并行计算的原因。
- 硬件结构与 CUDA 编程抽象的对应关系。

### 4. 一次 forward 如何在 GPU 上运行

基本路径：

**Python 模型代码 → PyTorch 算子 → 底层实现 → kernel 提交 → GPU 执行。**

- CPU 如何提交 kernel；stream 如何组织工作。
- 矩阵乘法、Embedding 查表、激活函数如何对应 GPU 工作。
- 一个 forward 通常触发多个 kernel。
- 模型中的一层不一定对应一个 kernel，算子融合会改变对应关系。
- 输入数据搬运、中间张量和同步如何影响耗时。

### 5. 性能分析与优化

将 CUDA、Triton、Nsight 放在这一节：它们属于编程与性能工具，不属于 GPU 硬件结构本身。

- 指标：延迟、吞吐量、显存占用、带宽利用率。
- 瓶颈：计算受限、访存受限、kernel 启动开销、同步、数据搬运。
- CUDA：GPU 编程平台与执行模型。
- Triton：编写高效 GPU kernel 的语言与编译工具。
- Nsight Systems（`nsys`）：查看 CPU、GPU、kernel 和数据搬运的整体时间线。
- Nsight Compute（`ncu`）：分析单个 kernel 的计算与访存表现。
- 优化方法：算子融合、减少中间数据、改善访存、混合精度、合理的 batch size。
- 测量要点：预热、正确处理异步执行、区分编译耗时和稳定执行耗时。
- 优化后同时验证数值正确性和性能，避免仅凭 GPU 利用率判断优化效果。

### 演示建议

1. 对同一个推荐模型运行 CPU 与 GPU 推理，说明数据规模与搬运开销的影响。
2. 观察一次 forward 的 GPU kernel 时间线。
3. 比较 eager 和 `torch.compile` 的稳定执行性能。
4. 选择一个简单算子，展示 CUDA / Triton 实现或融合示例。
5. 用 `nsys` 找到耗时区域，再用 `ncu` 分析一个代表性 kernel。

GPU、CUDA 和 Nsight 演示需要兼容的 NVIDIA GPU 环境；没有现场环境时，可使用事先录制的执行结果与性能报告。

## 第三场：大模型如何生成和服务

### 分享目标

理解 Transformer 生成一个 token 的过程，区分 prefill 和 decode，并解释 KV Cache、推理优化及 vLLM 如何支撑并发服务。

### 1. Transformer 的基本结构

- token 与分词：一个 token 不一定是一个汉字或一个单词。
- Token Embedding 与位置信息。
- Attention：Query、Key、Value 的作用，以及因果掩码。
- 多头注意力、MLP、残差连接和归一化。
- 输出 logits、采样或选择下一个 token。
- 用 decoder-only Transformer 作为本场的主要例子。

### 2. 一个 token 如何生成

基本过程：

**输入文本 → 分词 → prefill → 得到下一个 token 的分布 → 选择 token → decode → 重复直到结束。**

- 自回归生成：根据已有 token 预测下一个 token。
- Prefill：处理输入序列，并建立 KV Cache。
- Decode：利用已有 KV Cache，逐步生成后续 token。
- 首 token 与后续 token 的计算过程及延迟不同。
- Prefill 和 decode 的性能特征不同；实际瓶颈受模型、batch size、序列长度和硬件影响。

### 3. KV Cache

- 缓存历史 token 在各层的 Key 和 Value，避免每一步重复计算历史 K/V。
- Decode 的注意力仍需读取并使用历史 K/V。
- KV Cache 的规模与层数、序列长度、并发量、KV head 数、head 维度和 dtype 的关系。
- 长上下文和高并发为何增加显存压力。
- 区分模型权重、激活和 KV Cache 的显存占用。

### 4. 大模型推理优化

- FlashAttention：通过分块和减少内存读写提高 Attention 效率。
- FlashInfer：面向大模型推理的高效 GPU 算子库，包含 Attention 等实现。
- 投机解码：提出候选 token，再由目标模型验证；收益取决于候选接受率和额外开销。
- 混合精度与量化：减少存储和计算成本，并评估精度影响。
- 明确层次：Attention 算子优化、生成算法优化和服务调度优化解决不同问题。

### 5. vLLM 推理服务

- vLLM 的定位：大模型推理与服务引擎。
- 请求生命周期：接收请求 → 排队与调度 → prefill / decode → 输出 token → 释放资源。
- KV Cache 的分块管理与 PagedAttention 的基本思路。
- Continuous batching（连续批处理）：随执行进展动态加入和移除请求。
- 请求调度：安排哪些请求、哪些 token 在本轮执行，以及 token 与显存预算。
- 区分请求调度与底层算子执行：算子的执行还涉及编译器、算子库和 GPU runtime。
- 不同版本与配置可能采用不同 Attention 后端和调度策略，具体实现以演示版本为准。

### 6. 多 GPU 与分布式执行

- 张量并行：把同一层的计算拆分到多个 GPU。
- 流水线并行：把模型的不同层分配到不同 GPU。
- 数据并行 / 多副本服务：让不同副本处理不同请求。
- 通信开销、GPU 间互连和负载均衡的影响。
- 进阶扩展：prefill / decode 分离及其 KV Cache 传输成本。

### 7. 推理服务的评估指标

- 首 token 延迟（TTFT）。
- 后续 token 延迟（ITL）与每输出 token 耗时（TPOT），明确具体测量定义。
- 请求吞吐量与 token 吞吐量。
- 端到端延迟、并发能力与显存占用。
- 比较性能时固定或说明输入长度、输出长度、并发量、精度和硬件。
- 讨论吞吐量与延迟之间的取舍。

### 演示建议

1. 用短文本展示分词结果与逐 token 生成。
2. 画出 prefill、decode 与 KV Cache 的关系。
3. 展示多个请求在连续批处理中的加入和退出。
4. 使用 vLLM 运行推理请求，观察首 token 延迟与吞吐量。
5. 改变并发量和输入长度，观察延迟与显存变化。
